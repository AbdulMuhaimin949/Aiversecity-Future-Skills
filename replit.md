# Aiversecity Future Skills

Hackathon proof-of-concept (XMUM, Domain 1 "Future-Ready Workforce", Malaysia): takes a user from their current skills profile to an AI-era Future Skills Radar, explainable role matches with skill gaps, a reskilling pathway using HRD Corp e-LATiH resources, and UN SDG links, under baseline / moderate / fast disruption scenarios.

## Run & Operate

- `python pipeline/run_pipeline.py` — regenerate all Bronze/Silver/Gold CSVs (deterministic, seed 42); `pytest pipeline/tests`
- `pnpm --filter @workspace/api-server run dev` — API server (loads pipeline CSVs into memory at startup; restart after regenerating data)
- `pnpm --filter @workspace/future-skills run dev` — web app
- `pnpm run typecheck` — full typecheck across all packages
- `pnpm --filter @workspace/api-spec run codegen` — regenerate API hooks and Zod schemas from the OpenAPI spec
- `pnpm --filter @workspace/db run push` — enable pgvector and apply the Drizzle schema (`lib/db/src/schema/`) to the development database
- `pnpm --filter @workspace/scripts run db:import-catalogue` — repeatable import of source catalogue, occupations, skills and occupation-skill links from the pipeline CSVs (upserts by original ID; validates everything first and aborts with a row-level error list; each run is logged in `ingestion_runs` with a SHA-256 fingerprint of the CSVs). Rerun after regenerating pipeline data. `-- --if-changed` imports only when the CSVs differ from the last successful import or rows are missing. `db:catalogue-status` prints pgvector version, tables present vs. declared, and catalogue row counts.
- Production catalogue: the workspace cannot write to the production database, so the published API server runs the same import itself (`CATALOGUE_SYNC_ON_START=true` in the API server's production run env, `lib/catalogue` `syncCatalogue`). On each start it logs pgvector version, tables present (30 expected) and row counts, imports only when the database is behind the bundled CSVs, holds an advisory lock so parallel autoscale instances don't both import, and never creates tables or extensions (Publish applies the schema; if pgvector is reported missing, run `CREATE EXTENSION IF NOT EXISTS vector;` in the production database's SQL console and republish). Failures are logged and don't stop the API. Check the deployment logs for "Catalogue sync".
- `pnpm --filter @workspace/scripts run knowledge:ingest` — register knowledge documents (role profiles + e-LATiH courses from pipeline CSVs, markdown in `knowledge/methodology/`, fictional docs from `knowledge/synthetic-addon/rag_knowledge_documents.csv`, plus one fictional practice-lab doc per skill and one fictional demand-scenario doc per role from the learning/trend CSVs, validated against catalogue ids) as `pending` with chunks, then embed chunks of approved documents in approved sources. One `ingestion_runs` row per source with counts/errors. `-- --source "<name>"`, `-- --no-embed`.
- `pnpm --filter @workspace/scripts run knowledge:review -- --reviewer <email> --source "<name>" [--all-pending | --document <id>] --decision approved|rejected|needs_changes|retired` — approval decisions (history in `knowledge_approvals`, audit log); rerun ingest afterwards to embed. The same lifecycle is available in the app at `/admin/knowledge` (shared helpers in `lib/rag/src/documents.ts`). `knowledge:status [-- --pending]` lists sources, counts and recent runs.
- `pnpm --filter @workspace/scripts run db:import-synthetic-cvs` — repeatable import of the fictional demo CVs from `knowledge/synthetic-addon/` (profiles → `cv_documents`, claims → `cv_claims`, placeholder evidence → `cv_claim_evidence`, review-case ids → `cv_claims.review_case_id`); needs the catalogue first; validates everything before writing; keeps reviewer decisions and appeals on re-run; `-- --if-changed` like the catalogue import. The published API runs the same change-gated sync at startup after the catalogue (logs "Synthetic CV sync").
- `pnpm --filter @workspace/scripts run db:import-synthetic-learning` — repeatable import of the fictional practice labs (`synthetic_learning_resources.csv` → `synthetic_learning_resources` + `synthetic_learning_resource_skills`) and fictional quarterly demand index (`synthetic_trend_scenarios.csv` → `synthetic_trend_scenarios`); needs the catalogue first; validates every occupation/skill id and the synthetic markers (is_synthetic, NOT_AN_ACTUAL_COURSE, FICTIONAL_DEMAND_INDEX, rejects anything naming e-LATiH/HRD Corp) before writing; upserts by dataset id and removes rows no longer in the CSVs; `-- --if-changed` like the others. The published API runs the same change-gated sync at startup after the demo CVs (logs "Synthetic learning/trend sync").
- `pnpm --filter @workspace/scripts run cv:reviewer -- [--role reviewer|admin] --grant <email> | --revoke <email> | --list` — grants app roles in the development database. The reviewer desk accepts the `reviewer` or `admin` role; only admins can manage the AI Mentor knowledge base. In the published app, set `REVIEWER_EMAILS` and/or `ADMIN_EMAILS` (comma-separated) to bootstrap trusted accounts on their next request after Clerk verifies the email (audit-logged).
- The AI Mentor (floating "Ask AI" widget on every page, API `/api/assistant/*`) uses the official DeepSeek API for chat generation with `DEEPSEEK_API_KEY` in Replit Secrets and `DEEPSEEK_MODEL` (default `deepseek-flash`). Gemini remains separate for 768-dimensional `gemini-embedding-001` RAG embeddings and CV-review extraction; those features still require `GEMINI_API_KEY`. The Mentor is ready only when DeepSeek is configured and approved knowledge chunks are embedded. The rest of the app does not read the database. `DATABASE_URL` is only used by the schema push, the import, the knowledge/chat features and the production startup catalogue sync. Optional: an `OPENAI_API_KEY` secret (and `OPENAI_MODEL`, default `gpt-5-mini`) switches the CV scan to an AI model; without it the rule-based scanner is used.

## Architecture decisions

- The API serves the pipeline output loaded in memory (path resolved relative to the bundle `../../../pipeline/data` or `PIPELINE_DATA_DIR`). PostgreSQL backs the AI Mentor (chat/RAG) and the CV review demo.
- Database: catalogue tables use the pipeline IDs as primary keys; `data_origin` is `SOURCE_ATTRIBUTED` (pipeline marks non-synthetic and cites a source — not field-level verification) or `SYNTHETIC`. Languages `ms` (default), `zh-CN`, `en` are a reference table. Long FK names are declared explicitly (Postgres truncates names >63 chars, causing push drift); array columns have no default for the same reason.
- RAG (`lib/rag`): DeepSeek chat generation uses the official OpenAI JavaScript SDK against `https://api.deepseek.com`; `deepseek-flash` is the verified default. Gemini's official `@google/genai` SDK remains the separate embedding service: embeddings are fixed at 768 dimensions (`gemini-embedding-001`, `outputDimensionality: 768`, vectors L2-normalised, HNSW cosine index with iterative scan).
- `knowledge/synthetic-addon/` is the user's fictional hackathon dataset (README inside). `rag_knowledge_documents.csv` is imported as a knowledge source the CV profile/claim/evidence/review-case CSVs as demo CVs, and the learning-resource and trend CSVs into their own `synthetic_*` tables (served by `/api/synthetic/*`, shown in dashed amber "Synthetic demo data" panels: a fictional demand scenario on `/roles/:id` and fictional practice labs for gap skills on `/pathway/:id`). They are never merged into the pipeline forecasts, matching, pathway steps/hours or the e-LATiH catalogue (the API serves those from the pipeline CSVs). `synthetic_claim_test_oracle.csv` (and the `scenario_ground_truth` / `scenario` / `expected_training_action` columns) are evaluation answers: never read by the import, never in the database, so neither Gemini, applicants nor reviewers can see them.
- Approval gate: a chunk is retrieved only if its document AND its source are `approved`. Changing approval status never deletes stored documents or vectors; the strict retrieval gate keeps unapproved content out of answers. Changed documents become a new pending row (content hash); approving it retires the older approved version with the same title.
- Retrieval is free PostgreSQL full-text search (`lib/rag/src/lexical.ts`, lexical not semantic; ms/zh questions are mapped to English terms by a small glossary because approved docs are English). Gemini vector retrieval is no longer on the chat path. Status separates retrievalReady/embeddingReady/llmReady/chatReady; when DeepSeek's `/user/balance` says unavailable, replies are labelled search-only (not AI-generated).
- Assistant answers only from retrieved chunks (top 6); with none, a fixed localized "not in approved sources" reply is stored without calling DeepSeek. The model cites `[n]`; only cited chunks are stored in `chat_message_citations` (rank = n). Question and answer are stored together only when the answer succeeds.
- Chat identity: anonymous guest token in browser localStorage sent as a Bearer header; the server stores only its SHA-256 as `users.auth_subject` (`auth_provider = 'guest'`). In-memory rate limit: 20 questions / 10 min per guest, 200 globally.
- CV review demo (`/cv-review` applicant, `/reviewer` reviewer; API `/api/cv-review/*`, `/api/reviewer/*`): fictional evidence is stored as `simulated_document_metadata` with `verified_external = false` (DB check) and labelled as a placeholder in the UI. Gemini may only extract claims (once per CV, structured output; each quote must be found verbatim in the CV text and skill ids must exist, else dropped; stored `pending_review`). Only a signed-in reviewer changes a claim's status: EVIDENCE_SUFFICIENT / REQUEST_MORE_EVIDENCE / ESCALATED with a rationale, written to `review_decisions` + `audit_logs` in one transaction. Applicants appeal as guests (one appeal per decision, one open appeal per claim); while an appeal is open, the reviewer must resolve it (upheld must change the decision, stored as an extra claim decision) instead of deciding directly. Applicants never see reviewer identities; reviewers see applicants as pseudonymous "Guest applicant XXXXXX".
- Reviewer sign-in: Replit-managed Clerk (cookie session). Local `users` row with `auth_provider = 'clerk'`, `auth_subject` = Clerk user id; only verified emails are stored, and an email-only row created by `cv:reviewer --grant` is linked on first sign-in. Authorisation is the `reviewer` / `admin` row in `user_roles`. A signed-in visitor at `/` is redirected to `/reviewer` (admins without the reviewer role go to `/admin/knowledge`).
- Knowledge admin (`/admin/knowledge`, `/admin/knowledge/documents/:id`; API `/api/admin/knowledge/*`, admin role only): add a document (pasted text or .md/.txt read in the browser; defaults to the "Aiversecity admin uploads" source, created pending), approve / needs changes / reject / retire with notes (10+ chars), approve or reject whole sources, and an explicit "Generate embeddings" button (never automatic on approval). The AI Mentor only retrieves a chunk when the document and its source are approved and the chunk is embedded. Version = order among documents with the same title in the same source; approving a newer version retires the older approved one. Embedding runs are logged in `ingestion_runs` (`knowledge_embed`, max 300 chunks per request).
- Guest token vs Clerk: Clerk ignores the session cookie when an `Authorization` header is present, so `guestTokenMiddleware` (before `clerkMiddleware`) moves a guest token (32–128 url-safe chars, never a JWT) off the header; read it via `guestSubject(req)`.
- Match score follows the documented formula in `pipeline/ARCHITECTURE_AND_DATA_DICTIONARY.md` §2.1 exactly.
- Scenarios: pipeline moderate/fast values are near-uniform multipliers, so the API adds a displacement term `projected = V_s × (1 − λ·exposure·(1−augmentation))`, λ = 0 / 0.15 / 0.40, and widens the 90% band ×1 / 1.25 / 1.6. Direction = tertile within scenario. Documented in the radar `assumptions` text.
- Pipeline `pathway_steps` are only used when the resource's own `target_skill_ids` contains the expected outcome skill (only ~3/480 do); otherwise gaps are matched to catalogue resources, and unmatched gaps are listed as uncovered — courses are never invented.
- Outside the AI Mentor and CV review extraction (both Gemini), the only LLM path is the optional AI CV scan (needs the user's own OpenAI key): it may only pick taxonomy skill IDs and every skill must quote evidence found verbatim in the CV, else it is dropped. The About page disclosure switches automatically.
- CV scan: education from keyword rules (highest level found), years from an explicit "N years experience" phrase or merged date ranges under an Experience heading, industries ranked by detected skills used in each sector's roles (Core_Transferable excluded).

## Product

Pages: `/` overview, `/profile` intake (scan PDF CV or pasted text / synthetic persona / pick skills; scan results are reviewed before being added), `/radar`, `/matches`, `/roles/:id`, `/pathway/:occupationId`, `/sdgs`, `/about` (sources, metrics, AI disclosure), `/cv-review` + `/cv-review/:cvId` (fictional demo CVs: claims, AI extraction, review results, appeals), `/reviewer` + `/reviewer/cvs/:cvId` (signed-in reviewers: queue, decisions, appeal resolution, audit trail), `/admin/knowledge` + `/admin/knowledge/documents/:id` (signed-in admins: AI Mentor knowledge documents), `/sign-in`, `/sign-up`.

## Gotchas

- Trend data is simulated (`SYNTHETIC_SIMULATION`), anchored to MyCOL; labelled as estimates in the UI.
- Learning resource catalogue has only 14 entries (all tech/core), so many gaps — and all world-industry-specific gaps — show as uncovered.
- PDF scan needs a text-based PDF; scanned/photo CVs return a clear error (no OCR).
- Python deps for the pipeline are installed via the package manager (`pyproject.toml` at the repo root).
